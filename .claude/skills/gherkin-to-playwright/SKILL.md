# Gherkin → Playwright (playwright-bdd)

E2E tests live in `e2e/` (Nx project `e2e`, target `e2e`). Features are plain
Gherkin; `bddgen` compiles them into Playwright specs in `e2e/.features-gen/`,
which Playwright runs against a **target**: a tenant app (`E2E_APP`) in an
environment (`E2E_ENV`), resolved to website / editor / API URLs by
`support/targets.ts` (table in `e2e/README.md`). Deciding _what_ to write from a
branch's changes is the `gherkin-from-changes` skill; this one makes it run.

```
e2e/
  playwright.config.ts   # projects `website` + `editor`, baseURLs from the target
  features/website/      # Gherkin for tenant websites, one Feature per file, by domain
  features/editor/       # Gherkin for the editor
  steps/fixtures.ts      # the ONE test instance + Given/When/Then; custom fixtures go here
  steps/**/*.steps.ts    # step definitions by domain; editor-only ones in steps/editor/
  support/               # env/capabilities, GraphQL client, data factories, mailpit, checkout
  README.md              # env vars, local-stack and review-instance recipes
  .features-gen/         # GENERATED by bddgen — never edit, never commit
```

## Commands

| Goal                                      | Command                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------- |
| Run everything for a tenant               | `pnpm run e2e tsri,editor --environment staging` (or `E2E_APP`/`E2E_ENV`) |
| One application                           | `pnpm run e2e editor` / `pnpm run e2e tsri` (website)                       |
| Run by tag                                | `pnpm run e2e tsri --grep @smoke` (regex: `"@smoke\|@seo"`)              |
| List missing steps + paste-ready snippets | `cd e2e && pnpm exec bddgen`                                              |
| Debug headed / UI mode                    | `pnpm run e2e tsri --headed` or `--ui`                                    |
| Open HTML report                          | `pnpm run e2e:report` (Cucumber report: `e2e/cucumber-report/index.html`) |
| Typecheck steps                           | `pnpm exec tsc -p e2e/tsconfig.json --noEmit`                             |
| First run on a machine                    | `pnpm exec playwright install chromium`                                   |

Without env the target is `website-example` on the local stack: its own
API (:4010, database `wepublish_e2e`), website and editor, started and
migrated by the run, never your dev servers or dev database. `BASE_URL`,
`E2E_EDITOR_URL`, `E2E_API_URL` override single URLs (`E2E_`-prefixed because
Nx loads the root `.env`, which sets `API_URL`/`EDITOR_URL` for dev).
In CI the suite is **manual only**: Actions → "E2E tests" (`on-demand-e2e.yml`)
→ `app`, `environment` (+ `review_slot`), `project`, optional `grep` and
`allow_mutation`; the report is the `e2e-report`
artifact plus the job summary. It is deliberately not an Nx `test` target, so
`nx affected -t test` and `pnpm test` never run it.

## Workflow: feature -> green test (TDD applies)

1. **Read the feature.** If you are writing it, describe behaviour in the
   user's language (`Given I open the article "…"`), not UI mechanics
   (`When I click the div with class …`). One behaviour per scenario. Tag every
   scenario (`@smoke`, `@seo`, `@paywall`, …) so it can be filtered.
2. **Generate and watch it fail.** Run `cd e2e && pnpm exec bddgen`. It fails
   with "Missing step definitions" and prints snippets — that is the expected
   red. If it fails for any other reason (parse error, ambiguous step), fix
   that first.
3. **Reuse before you write.** Check `steps/common.steps.ts` and the other
   `*.steps.ts` files; rephrase the Gherkin to hit an existing step when the
   meaning is the same. Ambiguous matches (two definitions matching one step)
   are an error — never add a near-duplicate.
4. **Implement** the snippets in the matching domain file
   (`steps/<domain>.steps.ts`; create it if needed — any `steps/**/*.ts` is
   picked up). Keep each step small; push repeated page logic into a fixture.
5. **Run against a real site** and watch the new scenario pass:
   `pnpm run e2e <tenant> --environment … --grep "<scenario title or tag>"`. If it fails,
   read the error + trace (`pnpm exec playwright show-trace <zip>`) before
   changing code. Then run the full suite once.
6. **Typecheck** `e2e/` and report what you ran, against which URL, and the
   result.

## Step definition rules

- Import `Given`/`When`/`Then` **only from `./fixtures`**, never from
  `playwright-bdd` directly — otherwise the custom fixtures (`ctx`, page
  objects) are not available to the step.
- Use Cucumber expressions with typed params: `{string}`, `{int}`, `{float}`,
  `{word}`. Annotate the arg types (`async ({page}, slug: string) => …`).
- Step functions receive Playwright fixtures as the first argument: `page`,
  `request`, `context`, `baseURL`, plus our custom `ctx`.
- **Share state between steps through the `ctx` fixture** (extend
  `ScenarioContext` in `fixtures.ts`), never through module-level variables —
  scenarios run in parallel.
- Larger flows (login, paywall, comments) get a page-object fixture added to
  `test.extend` in `fixtures.ts`, not ad-hoc helpers in step files.
- Data tables: type the arg as `DataTable` from `playwright-bdd` and use
  `.hashes()` / `.rowsHash()`.

## Locators and assertions

- Prefer `getByRole` (with `name`), `getByLabel`, `getByText`,
  `getByPlaceholder`; fall back to `getByTestId` (`data-testid`) — add one to
  the component in `libs/*/website` if nothing semantic exists.
- **Never** select by MUI/emotion class names (`.css-1x2y3z`, `.MuiButton-root`)
  or deep CSS/XPath chains — they change between builds and tenants.
- Use web-first assertions that retry: `await expect(locator).toBeVisible()`,
  `toHaveText`, `toHaveAttribute`, `expect(page).toHaveURL/toHaveTitle`.
  **Never** `page.waitForTimeout` or manual sleeps.
- Use `request.get(path)` (relative paths resolve against the project's baseURL) for pure
  HTTP checks (status codes, headers, sitemap, feeds) — it's faster than a
  page load.
- Tenants differ in content and theme: assert on structure and behaviour
  (a title exists, a teaser links to an article), not on specific copy, unless
  the scenario is pinned to tenants with `@app:<name>` (e.g. `@app:bajour`;
  skipped for every other `E2E_APP`). Website features go in
  `features/website/`, editor features in `features/editor/` — the folder
  decides which app and baseURL a scenario runs against.

## Test data & fakes

Full details and recipes: [`e2e/README.md`](../../../e2e/README.md).

- **Capability tags gate scenarios.** `@mutating` (API URL, never
  production; off with `E2E_ALLOW_MUTATION=false`), `@payment` (simulated
  provider, never production), `@mail` (`MAILPIT_URL`), `@app:<name>`
  (only that tenant). The auto `capabilities` fixture skips a scenario
  with the reason when its env is missing, so production runs show these as
  skipped, never failed. Tag every scenario that writes data — that tag is the
  only thing keeping it off production.
- **`Given`s create state through the `data` fixture** (GraphQL API), never
  through UI clicks; it deletes what it created after the scenario. Add new
  entity builders to `support/factories.ts`, with a cleanup.
- **Named entities:** Gherkin uses a quoted alias (`a reader "Mia"`); the step
  stores the entity in `ctx.entities` and later steps resolve it with
  `data.get('reader', alias)`. Never hard-code seed content in steps.
- **Fakes:** mail is read from mailpit (`inbox` fixture), payment goes through
  the SIMULATED provider's checkout (`checkout` fixture, Pay / Decline /
  Cancel). Analytics, ads, Sentry and tracking pixels are blocked
  automatically; Turnstile uses the always-pass test keys and stays reachable.
- **Any other external provider has no fake** (Mailchimp, Stripe, Payrexx, …).
  Never mock it over HTTP and don't build a stand-in server. Either the user
  provides a real test account (below), or the journey is not E2E-able and a
  service spec covers it. If you hit this mid-implementation, stop and ask.
- **New capability for a test account:** `E2E_*` env vars read in
  `support/env.ts`, a `requirements` entry there (skip reason naming the
  vars), a row in the README's Capabilities table, `secrets.*` in
  `on-demand-e2e.yml`. Ask the user first. Readers' `e2e+…@example.test`
  addresses may be rejected by real providers, and data created there (list
  members, customers) is not deleted by `data`'s cleanup. Clean it up through
  the provider's API too, or say it stays behind.
- **Singleton settings** (the one mail / sync / challenge provider, global
  settings) are shared by every scenario running in parallel. A `Given` that
  changes them must restore what it read before (some fields, like API keys,
  cannot be read back). The suite runs `fullyParallel`, so scenarios
  changing the same singleton go in one feature tagged `@mode:serial`
  (playwright-bdd serialises per feature file, not across files).
- No secrets in feature files or steps. Credentials come from env vars read
  in `support/env.ts`, added to the workflow via `secrets.*` — ask the user
  first.

## Gotchas

- A Gherkin step that matches no definition fails at **generation** (`bddgen`),
  not at runtime — nothing runs until every step exists.
- After renaming a step's text, re-run `bddgen`; stale `.features-gen/` output
  is overwritten on each `pnpm run e2e`, so never hand-edit it.
- Content rendered client-side (e.g. some `<meta>` tags on tenant sites) only
  appears after hydration — web-first assertions handle it, but a raw
  `request.get()` + HTML string check will not see it. Pick the tool that
  matches what you are asserting (crawler-visible → `request`, user-visible →
  `page`).

# GraphQL & Prisma Workflow

Types flow in one direction. Follow it in order or you will generate against a
stale schema.

```
schema.prisma  ──migrate──▶  Prisma Client
      │
      ▼
libs/<domain>/api  (NestJS resolvers/models, code-first)
      │  running the API writes the SDL
      ▼
apps/api-example/schema-v2.graphql
      │  pnpm run generate-api
      ▼
libs/{editor,website}/api/src/lib/gql/graphql.ts  (+ schema-types.ts, possible-types.ts)
      │
      ▼
libs/<domain>/editor  &  libs/<domain>/website  (useQuery(XDocument))
```

## Prisma

Schema: `libs/api/prisma/schema.prisma` (configured via the `prisma` block in
the root `package.json`). Migrations: `libs/api/prisma/migrations/` — 158 and
counting, named `<timestamp>_<snake_case_description>`.

```bash
pnpm run start:docker                       # Postgres + MinIO + Dragonfly
pnpm prisma migrate dev --name add_foo_to_bar   # create + apply a new migration
pnpm prisma generate                        # regenerate the client (also runs on `pnpm install`)
pnpm run migrate                            # migrate deploy + seed (deploy path, CI/prod)
```

- **Never hand-edit a migration that has already been merged.** Write a new one.
- **Never edit generated Prisma client output.**
- Follow the existing naming style in `migrations/` — snake_case, descriptive.
- New IDs are UUIDv7, generated by Postgres: `@id
  @default(dbgenerated("uuidv7()"))` (built in since PG18, which is now the
  minimum). When code needs an ID before the row exists, use `v7` from `uuid`,
  not `crypto.randomUUID` (v4). Older rows keep their v4 IDs.
- Prefer real columns and relations over JSON blobs. A JSON column is acceptable
  only for a genuinely opaque payload with no per-element querying.
- Adding an index or a nullable column is cheap; renaming or dropping a column
  on a live table needs a staged migration. Flag destructive migrations to the
  user rather than generating them silently.

## GraphQL — code-first

The schema is **generated from NestJS decorators**, never written by hand.

```ts
@Resolver(() => Article)
export class ArticleResolver {
  @Query(() => Article)
  article(@Args('id') id: string) {}

  @ResolveField(() => [Tag])
  tags(@Parent() article: Article) {}
}
```

- `apps/api-example/schema-v2.graphql` is **generated output** (`autoSchemaFile`
  in `apps/api-example/src/nestapp/app.module.ts`). It is refreshed when the API
  runs in dev. Do not edit it by hand; if it is stale, start the API.
- Reuse models via interfaces and extension instead of writing new ones from
  scratch (see [code-style.md](code-style.md)).
- Use `@ResolveField` + a dataloader for relations. Resolving a relation with a
  direct Prisma call inside a list query is an N+1 — the `*-dataloader.service.ts`
  files in `libs/*/api` are the pattern to copy.
- Guard every field that exposes user or payment data with the permission
  decorators from `@wepublish/permissions/api`, and **test the deny path**.
- A class carrying **both** `@ObjectType('X')` and `@InputType('XInput')` is
  registered as two GraphQL types from one TS class, and Nest picks the right
  one per context (`InputTypeFactory` resolves by class target). That is how
  `BlockTiming` reaches every block input through `OmitType` without overriding
  the field in ~60 derived inputs — see
  `libs/block-content/api/src/lib/timing/`.

## Frontend codegen

```bash
pnpm run generate-api    # graphql-codegen -r dotenv/config --config codegen.yml
```

Reads `apps/api-example/schema-v2.graphql` plus the `.graphql` documents in
`libs/editor/api/src/lib/schemas/` and `libs/website/api/src/lib/schemas/`, and
emits, per lib, `src/lib/gql/graphql.ts` (one `TypedDocumentNode` per
operation), `schema-types.ts` (every schema type, enum and input) and
`possible-types.ts`. The hand-written `src/index.ts` barrel `export *`s all of
them. The peering client (`libs/peering/api/src/lib/remote/`) is generated the
same run. Every output is listed in `.prettierignore`. Codegen only writes
files; to check that the result compiles, typecheck the apps (see
[verification.md](verification.md)).

The editor/website targets run client-preset's plugins (`typescript-operations`
+ `typed-document-node`) **without** `preset: client`, on purpose:

- client-preset drops `importSchemaTypesFrom`, so its `graphql.ts` re-declares
  every enum/input an operation uses. That collides with `schema-types.ts`
  under `export *` (TS2308) and forced a generated by-name barrel.
- client-preset always writes `gql.ts`, the `graphql()` helper plus a second
  copy of every document. Nothing here uses it; documents are `.graphql` files.

Don't switch to `documentMode: graphQLTag` to shrink `graphql.ts`. It cuts the
file by about 88%, because fragments stop being inlined as JSON into every
document. But gzip already absorbs that (−2.5% on the editor bundle), and it
adds about 120 ms of `gql` parsing at module load to every page.

- Add or change a **document** (`.graphql` file) → rerun codegen → use the
  generated `XDocument` with Apollo's `useQuery` / `useMutation`.
- Never edit the output. If a type looks wrong, fix the resolver or the
  document and regenerate.
- A **new** codegen output must go into `.prettierignore`, or the pre-commit
  hook reformats it and every later codegen run shows a whole-file diff.
- `codegen.yml` is env-interpolated: `${name}` becomes the env var, so a scalar
  mapped to `` `${number}px` `` silently comes out as `` `undefinedpx` ``. Write
  `${ number }` (with spaces) in template literal scalar types.
- REST is only for external CMS connections. Everything internal is GraphQL.

## Blocks that are hidden or timed

`BaseBlock` carries `disabled` and `timing` (a single window of date range,
weekdays and time of day, all parts ANDed). **The api decides what shows, not
the website**: `ArticleRevision.blocks`, `PageRevision.blocks` and
`BlockTemplate.blocks` take `onlyDisplayed: Boolean = true` and drop hidden
blocks recursively, nested flex and template blocks included. The editor
documents pass `onlyDisplayed: false` because they edit the content; anything
built for display leaves the default alone and never looks at `disabled` or
`timing`. `shouldDisplay` resolves the same decision as a field, for the
editor's off-air badge. `onlyDisplayed: false` is only honoured for users who
can read articles (`CanGetArticle`), pages (`CanGetPage`) or, for templates,
edit them; everyone else silently gets the displayed blocks, and any request
asking for `false` skips the response cache.

Timed blocks also have to become visible on time: the revision resolvers cap
the answer cache through `limitAnswerCache(context, staleAt)` and publish the
next boundary as `blocksChangeAt`, which `revalidateFor` turns into a shorter
Next.js ISR window. The timezone comes from `TZ`, falling back to
`Europe/Zurich`. `blocksChangeAt` is the first moment the displayed tree
actually changes, so the timing code walks candidate instants rather than raw
boundaries.

- **Timings live in the revision's Prisma `Json` column, so `from`/`to` come
  back as ISO strings.** Everything in `timing/block-timing.ts` parses them
  first, and `BlockTimingResolver` turns them back into `Date` for the
  `DateTime` scalar, which serialises a string as `null`. Unreadable stored
  timings hide the block; `assertValidTiming` (called by `mapBlockUnionMap`)
  rejects them on save.
- **Don't use `getTimezoneOffset` from `date-fns-tz`** — it reports the old
  offset for the hour after a DST switch. Read the offset with
  `formatInTimeZone(date, tz, 'xxx')`.
- **Puck content (`ArticleRevision.puckBlocks`, `PageRevision.puckBlocks`) is
  pruned the same way**, with the same permission rule and cache handling,
  plus `puckBlocksChangeAt`. It is stored and written (`puckBlocks:
  [PuckBlockInput!]`) as a tree of API blocks, not Puck `Data`: the editor
  converts. Each block is `{id, type, data, locked?, visibility?, styling?,
  datasources?, slot?, children?}`: `type` is the component name, `data` the
  component props without those block fields and with every slot emptied to
  `[]`, `slot` the parent's slot path (`items[2].content`, omitted means
  `content`). It is **read flat** (`[PuckBlock!]`, depth first, with
  `parentId`/`slot`/`position`; `flattenPuckBlocks`), because a query cannot
  select a tree of unknown depth. `visibility`/`styling`/`datasources` are
  typed objects mirroring the editor's field values: enum values are named
  exactly as stored, union values use the `PuckSpacing`, `PuckMinHeight`,
  `PuckMaxWidth` and `PuckBackgroundPosition` scalars (mapped to template
  literal types in `codegen.yml`). Root props live in the revision fields and
  zones are not stored. The API never reads `data`; it only walks `children`.
  A block hides with its subtree through `visibility.disabled` /
  `visibility.timings` (plural, unlike `timing`) (`timing/puck-timing.ts`);
  breakpoints are left to the website. `parsePuckBlocks` (zod + date-fns) in
  `libs/puck-content/api` validates on save and normalises: nulls dropped,
  timings stored as UTC ISO strings, `flattenPuckBlocks` turns them back into
  `Date`. That lib must stay a leaf (only `authentication/api`), since
  article, page and block-content import it, so it has its own `PuckWeekday`
  instead of block-content's `Weekday`. Keep the website's `apiBlocksSchema`
  (`puck-content/website` `api-blocks.ts`) in step with it, or the editor
  cannot open what the API stored: the `storedBlockFormat` table is copied
  verbatim into both specs, so change it in both. The editor selects
  `...FullPuckBlock` (`editor/api` `schemas/puck-block.graphql`), rebuilds the
  tree with `toPuckData`, and saves through `toPuckBlockInputs`
  (`apps/editor/.../puck/puck-document-mapping.ts`), which maps the website's
  string values onto the generated enums. On update, an omitted `puckBlocks` or
  `blocks` carries over from the latest open revision, and an explicit
  `puckBlocks: null` clears it.

## Full end-to-end change checklist

Adding a field that reaches the website:

1. `schema.prisma` → `pnpm prisma migrate dev --name ...`
2. Write the **failing test** in `libs/<domain>/api` (see [testing.md](testing.md))
3. Model + resolver/service in `libs/<domain>/api` → test passes
4. Start the API so `schema-v2.graphql` regenerates
5. Add the field to the `.graphql` document, `pnpm run generate-api`
6. Failing spec in `libs/<domain>/website`, then the component
7. `pnpm nx affected -t lint test --uncommitted` — see [verification.md](verification.md)

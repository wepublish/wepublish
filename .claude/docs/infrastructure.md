# Infrastructure

## Cloud & Hosting

- **OpenShift** (self-hosted Kubernetes)
- **Helm** charts for deployment configuration (`helm/charts/`)
- **Flux** for GitOps-based deployments — not Argo CD. Flux's helm-controller
  reconciles a `HelmRelease` (`helm.toolkit.fluxcd.io/v2`) per app, and Flux's
  image-automation (`image.toolkit.fluxcd.io/v1` `ImagePolicy`, via the
  `$imagepolicy` markers) bumps image tags. Both halves are Flux.

## CI/CD

- **GitHub Actions** for all build, test, and deployment pipelines
- Review environments deployed per PR
- Docker images pushed to GitHub Container Registry (GHCR)

## Containerization

- **Docker** for local development (`docker-compose.yml`)
- Multi-stage Dockerfile for all production builds (API, editor, website, media, migration, storybook)
- **MinIO** as S3-compatible object storage for media in local dev

## Infrastructure as Code

- **Terraform** for infrastructure management
- This repo only *builds* images and *publishes* the Helm charts (charts go to a
  GitLab ChartMuseum on push to `master`, when `helm/charts/**/Chart.yaml`
  changes). Nothing here applies anything to a cluster. The `HelmRelease`
  objects that actually deploy the charts are generated by Terraform in the
  separate `application-configuration` repo
  (`terraform/modules/wepublish_app/templates/`), so a chart version bump has to
  land on `master` here *before* the pinned `version:` is raised there.
